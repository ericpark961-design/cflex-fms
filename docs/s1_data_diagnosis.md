### 왜 ACL이 아닌가

```
cflex-v2-vm (API + 프로브) : 10.0.0.5    Azure VNet 10.0.0.0/24
vm-cflex-probe-01 (VM1)    : 10.0.0.4    같은 VNet
터널 인터페이스             : 없음 (tun/wg/ipsec/gre 0개)

ip route get 10.112.0.76   → via 10.0.0.1 dev eth0     (기본 게이트웨이)
ip route get 10.119.143.129 → via 10.0.0.1 dev eth0
ip route get 10.189.193.220 → via 10.0.0.1 dev eth0

ping -c1 -W2 각 주소        → 0 응답
tcp/161 연결                 → closed/filtered
```

HAEA의 10.112 / 10.119 / 10.189 대역으로 가는 패킷이 Azure 기본 게이트웨이로 나가 버려집니다.
VNet 라우터는 그 대역을 모릅니다. **NMC가 우리 IP를 허용해도 패킷이 도착하지 않습니다.**

`vm-cflex-probe-01`은 이름만 프로브입니다 — API와 같은 VNet에 있고, 프로브가 설치돼 있지도 않습니다.

### 공문이 요구해야 하는 것 (수정)

기존 초안 방향(프로브 IP를 NMC ACL에 허용)은 **필요하지만 그것만으로는 아무것도 바뀌지 않습니다.**
선행 조건이 먼저입니다. 셋 중 하나를 HAEA에 요청해야 합니다.

| 방안 | 내용 | 리드타임 | 비고 |
| --- | --- | --- | --- |
| **A. 현장 프로브 호스트** | HMA·KUS·HQ 각 사이트에 미니 PC 또는 HAEA VM 1대. 아웃바운드 443만 (`cflex.runless.co.uk`). 인바운드 없음 | 가장 빠름 | 설계 의도였던 구성. 사이트별 1대 = 3대 |
| **B. Site-to-Site VPN** | HAEA ↔ Azure VNet IPsec. 10.112/10.119/10.189 → 10.0.0.0/24 | 중간 | HAEA 네트워크팀 승인 필요. 한 번에 3사이트 |
| **C. NMC만 DMZ/점프호스트 경유** | UPS NMC를 우리가 닿는 세그먼트로 이설 | 느림 | 44대 재주소 지정 — 권하지 않음 |

**A안 권고.** 프로브는 아웃바운드 전용으로 이미 그렇게 설계돼 있고, 방화벽 변경이 가장 적고,
KMX 서베이에서도 같은 방식으로 설치할 예정이라 구성이 하나로 통일됩니다.
A안이 되면 그 다음에 NMC ACL 허용 요청이 의미를 갖습니다 (프로브의 **사이트 내** IP를 허용).

KMX 5대도 같은 상태입니다 (10.60.1.x, no-route) — 10/27–11/7 서베이에서 프로브를 설치하면 해결됩니다.

## 3. 프로브가 거짓 보고를 하고 있었다

에이전트 로그 (10/11, 수정 전):

```
[probe] cycle: 41 ok, 0 fail, 420375ms
[probe] cycle: 41 ok, 0 fail, 420161ms
```

같은 시각 DB:

```
HMA      unreachable  28   consecutive_fails 최대 120,739
KUS      unreachable   7   consecutive_fails 최대   2,639
HAEA_HQ  unreachable   6   consecutive_fails 최대   2,254
```

원인: `pollers/ups.js`의 `pollDevice()`가 **성공과 실패 모두 `undefined`를 반환**했습니다.
호출부는 "호출이 돌아왔다"를 성공으로 셌습니다.

```js
// 전
await upsPoller.pollDevice(d);
ok++;                       // 타임아웃이어도 여기 도달

// 후
const r = await upsPoller.pollDevice(d);
if (r && r.ok === false) { fail++; lastError = r.error; } else ok++;
```

수정 후 같은 플릿: `cycle: 0 ok, 41 fail, 44032ms`.

### 부수 발견 — 5분 신선도 게이트를 구조적으로 통과할 수 없었다

직렬 폴링 × SNMP 타임아웃 3초 × (재시도 2+1) × 41대 = **420초**.
폴 간격은 60초이므로 매 틱이 `skip — previous cycle still running`.
**네트워크가 고쳐진 뒤에도** 어떤 장비도 5분 이내 신선값을 가질 수 없는 구조였습니다.

| | 전 | 후 |
| --- | --- | --- |
| 폴링 방식 | 직렬 | 동시 12 (`POLL_CONCURRENCY`) |
| 41대 주기 | 420 s | **44 s** |
| 60초 간격 적합 | ✗ (매 틱 skip) | ✓ |
| 5분 게이트 적합 | ✗ | ✓ |
| 주기 초과 시 | 조용히 skip | 경고 로그 + 조치 안내 |

### 알람 폭주도 같은 곳에서 나왔다

도달 불가 장비마다 **매 주기** P2 reachability 알람을 보냈습니다 → 10월 alerts 3,594행.
이제 상태 전이에 1회, 계속 다운이면 최대 1시간 간격, 복구 시 P4 1회.

## 5. "5분 내 신선"이 성공을 뜻하지 못했다

`last_polled`는 **실패해도 갱신**됩니다. 시도 시각이지 수집 시각이 아닙니다.
그래서 진단 시작 시점에 41대가 "5분 내 신선"으로 집계됐고, 그 41대 전부가 타임아웃이었습니다.

007 마이그레이션에 `ups_devices.last_ok_polled` / `fms_devices.last_ok_polled`를 추가했습니다.
**Exit 기준 2번("5분 이내 신선")은 이 컬럼으로만 답할 수 있습니다.**

> v4 브리프의 "`ups_devices` 변경 금지"에서 의도적으로 벗어난 부분입니다.
> 추가 컬럼이고 기본 동작 변화가 없어 1.x에 영향은 없습니다. 기록을 남깁니다.
